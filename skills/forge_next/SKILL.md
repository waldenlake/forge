# /next

`/next` is a thin loop over `forge run-loop`. It does not contain
phase-routing logic, guard-decision logic, task-selection logic, or
any knowledge of `run-cli` actions. All deterministic workflow steps
are consumed internally by the CLI.

## Forge CLI

Before calling any Forge Runtime command, resolve the executable.

**bash / zsh / Git Bash** — use the `FORGE_CMD` resolver:

```bash
FORGE_CMD=$(command -v forge 2>/dev/null || { if [ -f "$HOME/.config/opencode/plugins/forge/cli/dist/index.js" ]; then echo "node $HOME/.config/opencode/plugins/forge/cli/dist/index.js"; else echo ".forge/bin/forge"; fi; })
```

**cmd.exe / PowerShell** — use the project-local wrapper directly:

```cmd
.\.forge\bin\forge.cmd <subcommand>
```

The wrapper at `.forge/bin/forge` (POSIX) and `.forge/bin/forge.cmd` (Windows)
is generated by `forge init` and forwards to the installed CLI (global `forge`,
OpenCode plugin install, or `node_modules/@forge/cli`).

All Runtime commands output JSON. Parse the JSON silently, extract only
relevant fields, and present results using SKILL-UX.md templates. NEVER
display raw JSON to the user. Do not edit `.forge/*.json` directly.

## Output Format

Follow `skills/SKILL-UX.md`.

**Header**:

```
⚒ Forge  ·  /next
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## Flow — the run-loop driver

### Step 1: Call run-loop

Run (bash):

```bash
$FORGE_CMD run-loop
```

Or (PowerShell / cmd):

```cmd
.\.forge\bin\forge.cmd run-loop
```

If the command cannot be resolved (forge CLI not found):

```
✘  forge CLI not found
```

STOP.

### Step 2: Dispatch by action

| Field | Dispatch |
|-------|----------|
| `action: "invoke-skill"` | Invoke the named `skill` with its `args`. If a `record` field exists, run that `guard:record` command after the skill returns. Then go to Step 1. |
| `action: "handoff-session"` | Context-manager plugin signaled a session handoff. The platform hook will execute the restart in the background. **You MUST stop and emit the SKILL-UX STOP block below — do NOT loop, do NOT pick up the next task.** |
| `action: "suggest-compact"` | Context occupancy is high but no in-place restart path is available. **You MUST stop and emit the SKILL-UX STOP block below — do NOT loop.** |
| `action: "wait-human"` | Output `reason` and `recovery` (if present). STOP. |
| `ok: false` | Output `error` and `recovery` (if present). STOP. |

Output for `handoff-session` (`method` is `"in-place"` or `"new-window"`):

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⏸  Context handoff — <reason from CLI>
▸  Next: session restarts automatically (<method>); /resume on new context
```

Output for `suggest-compact`:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⏸  <reason from CLI> — recommend compacting at this task boundary
▸  Next: run /compact, then /resume to continue
```

These two actions are **terminal for this turn**. The user (or the platform
hook) will resume forge in a fresh context. Picking up the next task here
defeats the entire context-management mechanism.

That's it. No `run-cli` handling, no `after` instructions, no `guard:run`.
The CLI consumed all deterministic steps internally before returning.

### Step 3: Obey `reminder`

Every successful output carries a `reminder` field. Obey it: you are a
Forge execution agent. Execute exactly what `run-loop` returns. Do not
improvise, skip steps, or substitute your own judgment for the CLI's
routing decision.

## Error Handling

| Condition | Output |
|---|---|
| Forge CLI not found | `✘ forge CLI not found` |
| `ok: false` | `✘ <error>` (+ `recovery` if present) |
| `action: "wait-human"` | Output `reason` (+ `recovery` if present) |

## Dependencies

- **Forge CLI Runtime** — `run-loop`.
- **/planning, /executing, /verify, /done** — phase skills invoked via `invoke-skill` actions.
